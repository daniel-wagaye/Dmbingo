Database design
SUPABASE Database Tables (PostgresSQL)

users
Stores each player.
CREATE TABLE  users (
    telegram_id BIGINT PRIMARY KEY,              -- Telegram unique ID
    phone_number VARCHAR(25) UNIQUE,                   -- User phone number from telegram
    username TEXT,                              -- Telegram @username
    first_name TEXT,                            -- Telegram name
    withdrawal_wallet NUMERIC(12,2) DEFAULT 0,  -- money player can withdraw
    non_withdrawal_wallet NUMERIC(12,2) DEFAULT 0, -- non_withdrawable/only for playing game
    referral_count INT DEFAULT 0,               -- number of referrals
    last_referred_date TIMESTAMPTZ,
    language TEXT CHECK (language IN ('en','am')) DEFAULT 'en',
    created_at TIMESTAMPTZ DEFAULT NOW()
);

admins
All admin credentials
CREATE TABLE admins (
  admin_id BIGSERIAL PRIMARY KEY,
  username TEXT UNIQUE NOT NULL,
  login_password_hash TEXT NOT NULL,
  action_password_hash TEXT NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('super_admin','withdrawal_admin')),
  first_name TEXT,
  last_name TEXT,
  email_address TEXT, -- only for super admin(it helps the super admin to change their action, login and email adress by sending otp to this email)
  is_active BOOLEAN DEFAULT TRUE,
  failed_login_attempts SMALLINT DEFAULT 0,  -- NEW: tracks sequential failed logins; resets on success
  locked_at TIMESTAMPTZ,                     -- NEW: timestamp when account was locked (set on lock, cleared on reactivation)
  last_login TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ
);

admin_otps
admin_otps (store OTP metadata; OTPs hashed with HMAC-SHA256)
CREATE TABLE admin_otps (
  id bigserial PRIMARY KEY,
  admin_id bigint REFERENCES admins(admin_id) ON DELETE CASCADE,
  purpose text NOT NULL,         -- 'password_change'|'email_change_current'|'email_change_new'
  sent_to text NOT NULL,         -- email address that received this OTP
  otp_hash text NOT NULL,        -- HMAC-SHA256(otp + server_secret)
  created_at TIMESTAMPTZ DEFAULT NOW(),
  expires_at TIMESTAMPTZ NOT NULL,
  is_used boolean DEFAULT false, -- set true on successful verify
  is_active boolean DEFAULT true,-- set false when another OTP is issued or expired
  attempts smallint DEFAULT 0,   -- number of verify attempts
  ip_address text,
  user_agent text
);

CREATE INDEX idx_admin_otps_admin_created ON admin_otps(admin_id, created_at);
CREATE INDEX idx_admin_otps_admin_active ON admin_otps(admin_id) WHERE is_active = true;

Admin Web App 
Build a modern admin web app to manage the DM Bingo backend. Two roles: Super Admin, Withdrawal Admin. Left-side navigation. Responsive, computer-first admin UI with a clean dark textured background option + light theme; use glossy cards, rounded corners, subtle shadows, Poppins or Inter font, neon orange primary accent and cyan secondary accents. Use server-side pagination + search (no client-only search).
All sensitive actions require re-entry of the admin action password in a modal every time. (Super Admin and Withdrawal Admin only).

Global behaviors
Secure login with HTTPS, short-lived JWT + refresh token in http-only cookie.
Password storage: strong hashing (argon2) + unique salt. Enforce 8+ char strong passwords for admins.
All admin actions logged to admin_actions with: admin_id, action, target_id, payload (JSON), ip, user_agent, created_at.
UI: show toasts for success/error messages. Confirm modals for destructive actions.
Table behavior: fetch 200 rows per page by default; server-side pagination links at bottom to access other pages. Server-side search queries the DB (not just the loaded 200 rows).
Date filter (from — to) for Users, Deposit, Pending Withdrawals, Approved Withdrawals.
Accessibility: keyboard-first modals, aria labels.

Action Password Logic:
Super Admin and Withdrawal Admin have a separate action password for sensitive actions such as approving withdrawals, rejecting deposits, crediting users, changing stake, and creating coupons.
Backend verification checks:
argon2.compareSync(entered_password, admin.action_password_hash)
If incorrect, backend returns 401 with toast.error("Incorrect action password").

Admin JWT Authentication
Use secure JWT authentication for the admin web app:
Access Token (short-lived) → expires in 15 minutes.
Refresh Token (long-lived) → expires in 1 day.
Both tokens are signed with strong secrets and stored in HTTP-only, Secure cookies.
On login → verify admin credentials (argon2).
On success → issue both tokens and update admins.last_login.
On refresh → validate refresh token and issue new access token.
On logout → clear both cookies.
Protect all admin endpoints using middleware:
authenticateAdmin → verifies access token.
authorizeRole('super_admin' | 'withdrawal_admin') → restricts by role.
If access token expires → frontend automatically calls /auth/refresh.
All requests sent with axios.withCredentials = true.

UI/UX and Styling
Layout: Design a responsive, computer-first layout featuring a central login form presented as a glossy card.
Theme: The page should have a clean dark textured background but also support a light theme option.
Aesthetics: Use rounded corners and subtle shadows to create depth. The primary accent color should be neon orange, with cyan for secondary elements.

Form Fields: Include input fields for username and password, along with a primary action button labeled "Log In".
under a clickable "Forgot Password" text.
Authentication and Security Logic
Credential Verification: Upon submission, the page will send the admin's credentials to the backend, which will verify them against the stored argon2 hash.
JWT Issuance: On successful login, the backend will issue two tokens and store them in HTTP-only, Secure cookies:
An Access Token with a short lifespan (15 minutes).
A Refresh Token with a longer lifespan (1 day).
Redirection: After a successful login, the user should be redirected to their role-specific default route.

Super Admin & Admin Lockout / Recovery

There is exactly one super_admin account. If that Super Admin accumulates 10 sequential failed login attempts (a successful login resets the failed counter), the account is immediately deactivated (is_active = false) and must be reactivated only by sending OTP code to their Email adress by clicking forget password.

withdrawal_admin is locked after 5 sequential failed login attempts. Locking sets is_active = false and locked_at = now(). Only a Super Admin may reactivate them via the Admin Management page.

A failed attempt is counted only if the submitted username exists in admins.username. Attempts with non-existent usernames must be handled identically from the client perspective (generic error) but must not increment any existing admin's failed counter.

All lock/unlock/recovery/password-reset/login events are recorded in admin_actions with relevant metadata (action, admin_id, target_id, target_type, details JSON, ip_address, user_agent, created_at).

Login attempt semantics
On each login attempt:
Look up admins by username. If no matching username, return a generic login failed response (do not increment or create any counters).
2. If username exists and is_active = false:
If role = super_admin return a response telling the client: "The account is deactivated".
For other admins, return "Account locked — Reach out Super Admin for reactivation."
Log the login attempt to admin_actions with action login_attempt and details { result: 'locked' }.
3. If username exists and is_active = true, verify password (argon2).
If password is correct:
    - Reset failed_login_attempts = 0.
    - Update last_login = now().
    - Create admin_actions record: action login, details { result: 'success' }, plus ip_address and user_agent.
If password is incorrect:
    - Increment failed_login_attempts atomically for that admin row.
    - Create admin_actions record: action login_attempt, details { result: 'bad_password', failed_login_attempts: <new_value> }, plus ip_address and user_agent.
    - If the incremented failed_login_attempts reaches the lock threshold (10 for super_admin, 5 for others) then:
         - Set is_active = false, set locked_at = now().
         - Insert an admin_actions record: action account_locked, details { by: 'failed_attempts', threshold: <n>, failed_login_attempts: <n> }, plus ip_address and user_agent.
Return generic login failed message.

Forget Password flow (UI + backend contract, plain text)
1. Trigger
- On the sign-in card there is a clickable text button labeled: Forgot Password?
- When clicked, the sign-in form switches to the Forgot Password flow (same card).
2. Step A — Enter username
- Show a single input: Username and a primary button: Continue.
- Client POST /admin/forgot with { username }.
- Backend behavior:
  - If username not found → return 404 with { error: "unknown_username" }.
    - Frontend shows toast.error("Unknown Username!").
  - If username exists and role === "withdrawal_admin" and is_active === false:
    - Return 200 with { status: "locked_withdrawal_admin" }.
    - Frontend: show a green helper text under the username input: "Please reach out to Super Admin for reactivation." Do not offer an OTP/email path to withdrawal admins.
  - If username exists and role === "withdrawal_admin" and is_active === true:
    - Return 200 with { status: "active_withdrawal_admin" }.
    - Frontend: Toast.error("Please contact Support") (no OTP flow).
  - If username exists and role === "super_admin":
    - Return 200 with { status: "super_admin" }.
3. Step B — Confirm super admin email
- If backend returned super_admin:
  - Show second input field labeled "Enter your current email address".
  - On submit, client POST /admin/forgot/verify-email with { username, email }.
  - Backend checks email equality (case-insensitive) to the stored admins.email_address.
    - If mismatch → return 400 { error: "email_mismatch" }. Frontend shows toast.success("A Link is send to Your email Adress seccesfully").(it will make an illusion that the hackers think that they entered correct email adress or will recieve a recovery link).
    - If match → backend:
      - Generate a numeric 6-digit OTP (random 000000–999999).
      - Store OTP metadata in admin_otps (or similar): admin_id, purpose='reactivate', otp_hash (HMAC-SHA256 or bcrypt/argon2 of the OTP + server secret), expires_at = now + 5 minutes, is_active=true, attempts=0.
      - Send OTP via configured email service Resend with a short message and mention the 5-minute expiry.
      - Log an admin_actions record: action='forgot_password_sent', target_id=admin_id, details includes via: 'email'.
      - Return 200 { status: "otp_sent" }.
  - Frontend on success shows toast.success("A verification code has been sent to your email address.") and reveals the OTP entry UI.
4. Step C — Enter OTP
- UI: single input accepting exactly 6 numeric digits and a primary button Validate.
- Also show:
  - small text: "Didn't get it? Resend" (Resend disabled for 60 seconds after send).
  - show OTP expiry countdown (derived from backend expires_at if provided).
- On Validate click: client POST /admin/forgot/validate-otp with { username, otp }.
- Backend validation rules:
  - Lookup latest active admin_otps for admin_id + purpose 'reactivate'.
  - If none found → return 400 { error: 'no_active_otp' }.
  - If expires_at < now → mark OTP is_active=false, return 410 { error: 'otp_expired' }.
  - If attempts >= 5 → mark is_active=false, return 429 { error: 'too_many_attempts' }.
  - Compare OTP by hashing submitted OTP with same HMAC/secret and comparing otp_hash.
    - If invalid → increment attempts, return 401 { error: 'invalid_otp', attempts_left: X }.
    - If valid → mark OTP is_used=true, is_active=false.
      - Reactivation logic: set admins.is_active = true, failed_login_attempts = 0, locked_at = NULL (only if account was deactivated by failed attempts).
      - Log admin_actions: action='reactivate_via_otp', target_id=admin_id.
      - Return 200 { status: 'reactivated', redirect: '/admin/dashboard', role: 'super_admin' }.
- Frontend behavior:
  - On invalid_otp show toast.error("Invalid code. X attempts left.").
  - On otp_expired show toast.error("Code expired — please resend.") and reveal Resend control enabled.
  - On too_many_attempts show toast.error("Too many attempts. Please contact support.").
  - On success (200) → redirect the user to /admin/dashboard as Super Admin (do not reset the login password).
5. Resend OTP
- Client POST /admin/forgot/resend-otp with { username }.
- Backend:
  - Enforce resend cooldown (e.g., 60 seconds) and only 5 OTP email limit in 3 hours.
  - Invalidate previous admin_otps for this admin_id/purpose and create a fresh OTP record (new otp_hash, new expires_at).
  - Send email and log admin_actions: action='forgot_password_resent'.
  - Return 200 { status: 'otp_resent', next_resend_allowed_at: <TIMESTAMPTZ> }.
  - Frontend: disable Resend until next_resend_allowed_at.
6. UX & Accessibility notes
- All toasts and helper text must be accessible and announced by screen readers.
- Modals and focus trapping are not required — the flow lives inside the login card — but ensure inputs are keyboard accessible and labelled (aria-label, aria-invalid when needed).
- Error strings shown to the user should be user-friendly; internal error codes can be returned by API for logging.
7. Security & audit considerations (must be implemented on backend)
- Store OTP hashed (never store plaintext OTP).
- OTP expiry: 5 minutes.
- OTP attempts: max 5 attempts per OTP.
- Resend cooldown: 60 seconds; daily resend limit (e.g., 5).
- Rate-limit requests to /admin/forgot* endpoints to prevent enumeration/brute force.
- Log every step in admin_actions (forgot_request, forgot_password_sent, forgot_password_resent, reactivate_via_otp, invalid_otp_attempt) with ip_address and user_agent.
- Consider avoiding explicit “Unknown Username” replies to reduce user enumeration; if you must show it, do so consistently across your app.

Admin Management Page (Super Admin only)
Purpose: The Super Admin can create, edit, activate/deactivate.
UI / Layout:
  - Page header: Admin Management. Top-right primary button: Create Admin.
  - Main content: full-width table (server-side pagination, default page size 200) with columns:
      - Admin ID
      - Role (super_admin | withdrawal_admin)
      - First name
      - Last name
      - Username
      - Created At
      - Is Active (toggle)
      - Actions (Edit button)
  - Table supports server-side search (username, first/last name) and sorting on created_at.
  - Accessibility: keyboard-accessible modals, ARIA labels for controls.

Create Admin Modal
Fields:
 - Role withdrawal_admin.
 - Username — required, unique, 3–32 chars (A-Za-z0-9_-).
 - First name — required.
 - Last name — optional.
 - Login Password — required, min 8 chars, must have uppercase letter, lowercase letter, special caracters and numbers.
 - Action Password — required min 8 chars, must have uppercase letter, lowercase letter, special caracters and numbers.
 - Super Admin Action Password — required to confirm creation.
Buttons: Close, Create (disabled until client-side validation passes).
Behavior: client-side validation → POST to server → on success close modal, toast success, refresh table.
Store login/action passwords hashed (argon2)

Edit Admin Modal
 - Top: selector to choose what to edit: Username | Login password | Action password | All.
 - Show inputs based on selection:
   - Username → username input
   - Login password → password input
   - Action password → password input
   - All → username + login password + action password
 - Below inputs: Super Admin Action Password (required).
 - Buttons: Close, Change (disabled until inputs + super-admin-action-password valid).
 - On submit: validate and call server PUT; show inline server errors; toast & refresh row on success.
  -  Store login/action passwords hashed (argon2)

Activate / Deactivate Toggle
 - Each row has an active/inactive toggle.
 - When toggled, open a confirmation modal requiring Super Admin Action Password.
 - Buttons: Close and OK.
 - On OK: call server endpoint to change is_active. Server validates super admin action password and returns success/failure; update UI.

Validation rules
 - Username: unique, 3–32 chars, allowed A-Za-z0-9_-.
 - Passwords: min 8 chars; require complexity (upper, lower, number, symbol) or at least 8 chars.
 - Action password required for withdrawal_admin and super_admin.
 - Re-verify Super Admin Action Password server-side for all sensitive operations.

PASSWORD POLICY (client + server)
- Requirements:
  - Minimum length: 8 characters
  - At least one uppercase letter
  - At least one lowercase letter
  - At least one digit
  - At least one symbol (non-alphanumeric)
- Confirm new password must exactly match new password.
- Client must show inline, specific error messages when the password does not meet each rule. Example messages:
  - "Password must be at least 8 characters."
  - "Password must contain at least one uppercase letter."
  - "Passwords do not match."
- Server must re-validate the same policy regardless of client validation.

OTP LIFECYCLE & RULES (server-enforced)
- Format: 6-digit numeric code (000000–999999).
- Generation: cryptographically secure random generator.
- Storage: server MUST store only the HMAC-SHA256 of the OTP using a long OTP_SERVER_SECRET. Never store the plain OTP.
- Validity window: 5 minutes from creation.
- Single-use: OTP is one-time. On successful verification, mark OTP used and inactive.
- When issuing a new OTP for the same admin and purpose:
  - In a single atomic transaction deactivate any previous active OTPs for that admin and purpose (set is_active=false).
  - Insert new OTP record with expires_at = now + 5 minutes and is_active=true.
  - This guarantees earlier codes immediately become invalid.
- Brute-force policy:
  - Each OTP row has an attempts counter.
  - On every failed verify increment attempts.
  - If attempts >= 5 → set is_active=false and log as blocked.
- Rate limits when sending OTPs (all enforced server-side; UI must reflect them):
  - Max 10 OTP sends per admin per rolling 2-hour window.
  - Cooldown: cannot send more than one OTP within 60 seconds. UI disables send button and shows countdown seconds remaining.
- All time comparisons use server time.

ERROR MESSAGES
- For invalid email provided by super admin when requesting OTP:
  - "The current email address you entered is incorrect."
- For cooldown when Send Verification Code pressed too soon:
  - "Please wait {seconds} seconds before requesting another code."
- For rate limit exceeded:
  - "You have reached the maximum number of verification requests. Please try again later."
- For OTP invalid or OTP expired:
  - "The verification code is invalid. Please try again."
- For current action password incorrect (withdrawal admin):
  - "Current Action Password is incorrect."
- On success (password updated):
  - "Password updated successfully."
- On success (email updated):
  - "Email address updated successfully."
