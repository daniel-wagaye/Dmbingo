picking phase page
1. Key design constraints (do not change)
 - Buffer model: player_picks table has 500 prepopulated rows. board_id and bingo_card are immutable.
 - Single endpoint: POST /api/games/:gameId/pick handles pick, move-pick, mandatory unpick. Note: the server ignores the path parameter :gameId and derives the acting game id from the current (last) games row — i.e. SELECT max(game_id) FROM games.
 - Server setTimeout controls picking window. No DB-time checks in pick endpoint.
 - Wallet fetched on app start and whenever a new picking phase is detected (clients update local wallet on pick/unpick success).
 - game_config contains stake_amount, picking_countdown_end_time (seconds), minimum_player, prize_percent.
 - RLS is enabled for games and player_picks so clients only see the active game (max(game_id)).
 - The client application must bundle all 500 bingo cards locally (e.g., const BINGO_CARDS = {...}) so previews are rendered with zero latency. That bundle must be generated from the exact same generator/script used to prepopulate the player_picks.bingo_card column to guarantee perfect sync. The server remains the source-of-truth for winner validation (reads from DB).

2. UI (Frontend) — exact visual + interactive behavior
Route: /game_picking
Top stat row (three glossy boxes, horizontal)
 - Left (large): Countdown — bold glowing orange. Implement by computing: timeLeftMs = Date.parse(games.picking_ends_at) - Date.now() using UTC. Update locally (e.g., 250–500ms tick).
 - Middle: Wallet total in white: users.withdrawal_wallet + users.non_withdrawal_wallet. Fetch on app load and whenever a new picking phase is detected.
 - Right: Stake (games.stake_amount) in white.
Styling: glossy highlights, rounded corners, soft shadows.

Body — 1..500 tile grid
 - Small Rounded square tiles (1..500). Visual states:
   - Unpicked (for current game): cool gray with white number.
   - Picked by other (row.game_id === currentGameId && row.telegram_id !== me): bright orange.
   - My pick (row.game_id === currentGameId && row.telegram_id === me): deep green.
 - Click behavior:
   - Click green (your) tile → unpick immediately (mandatory).
   - Click gray tile → pick (or move-pick if you already had a pick).
   - Click orange tile → disabled.
 - UX rules:
   - Show spinner on clicked tile while awaiting server + realtime confirmation.
   - Do not flip tile color optimistically; wait for Supabase Realtime UPDATE to confirm.
   - Debounce clicks: 1 request per 600ms per user.
Footer — 5×5 bingo preview (show/hide logic)
 - Show preview only when player has a confirmed pick for currentGameId.
   - If user has no pick → footer hidden.
   - On successful pick → footer shows 5×5 preview using the bundled client mapping board_id → bingo_card (pre-loaded in the app for zero-latency preview).
   - On move-pick → update preview from the bundled mapping.
   - On unpick → hide preview.
   - On load, if user already has pick for current game → show preview (rendered from the preloaded client bundle).
 - Client generates preview locally from the preloaded mapping; client does not send bingo_card with pick (server reads prepopulated player_picks.bingo_card if needed).
   Style: B/I/N/G/O colored headers; center cell is “FREE” (green); glossy polish.

3. Client realtime & local logic
Subscriptions
Subscribe to:
 - games (latest row) to detect new game id & phase changes.
 - player_picks (all rows). RLS ensures only active-game rows are visible.
Initial load
Fetch:
 - latest games row → set currentGameId, picking_ends_at, stake_amount.
 - wallet values once: users.withdrawal_wallet, users.non_withdrawal_wallet.
 - all player_picks rows (RLS returns only rows matching active game).
 - load the bundled BINGO_CARDS (client-side BINGO_CARDS object) on app start so the footer preview is available instantly.
When clients see a new games row with phase='picking' (i.e., a new game started), re-fetch wallet once and re-fetch player_picks (Realtime will deliver updates but fetch ensures sync).

Realtime
 - On player_picks UPDATE: update only affected tile(s) (green/orange/gray).
 - On games INSERT/UPDATE (phase change): detect new game or started and act accordingly (reload wallet on new picking, stop accepting picks on started).
Wallet
 - Do not subscribe to wallet realtime. Fetch at app load and on new picking phase detection. Update the local wallet value when server confirms pick/unpick.

4. Single endpoint: POST /api/games/:gameId/pick
Request contract (client → server):
 - Headers:
   - x-telegram-init-data: <Telegram initData string> — client MUST include the Telegram WebApp initData string in a request header.
     - The server must verify the initData signature using Telegram's recommended verification (bot token) and extract the telegram_id from the verified initData.
     - If signature verification fails → server returns 401 Unauthorized.
     - If header doesn't exist → server returns 401 Unauthorized.
       Body (JSON):
       { "board_id": 42 }

- Important: the client must not send telegram_id in the request body. Important: the server ignores the path parameter :gameId and derives the acting game id from the current last games row (SELECT max(game_id) FROM games). The server uses the telegram_id extracted from verified initData as the acting user identity.

High-level behavior (single transactional endpoint)
 - Unpick: if clicking own slot → refund and clear ownership (do not change board_id or bingo_card).
 - First-time pick: if no previous pick → verify balance, debit (withdrawal first then non-withdrawal), claim slot and store used amounts.
 - Move-pick: if user had a pick → clear old slot and claim new slot transferring stored used amounts (no extra debit).
 - Race: if target slot is taken by someone else for same game_id → 409 BOARD_TAKEN.
 - User missing rule: After verifying initData and extracting telegram_id, the backend must check whether telegram_id exists in users. If the user does not exist, the backend must abort silently: do no writes, do not emit realtime events, and return 204 No Content. (This is deliberate: silent abort, no errors shown to the client.)
 - All done inside a single DB transaction with strict lock ordering. Backend uses service role for writes.

5. Sliding-window rate limiting (per-user, in-memory) — exact implementation
Goal: limit abusive pick/unpick attempts; use an in-memory sliding-window per-user rate limiter run before any DB work or validation.
Data structure
 - Module-scoped Map<number, number[]> where key = telegram_id and value = array of timestamps in milliseconds.
 - Example (Node/TS):
   const pickRateLimitMap = new Map<number, number[]>(); // telegram_id -> [tsMs,...]
   const PICK_RATE_LIMIT_WINDOW_MS = 60_000; // 60 seconds
    const PICK_RATE_LIMIT_MAX = 5; // max requests allowed in the window (per-user)

Per-request algorithm (run at the very top of POST /api/games/:gameId/pick handler, before DB queries/locks)
A. const now = Date.now();
B. let timestamps = pickRateLimitMap.get(telegram_id) || [];
C. timestamps = timestamps.filter(ts => now - ts < PICK_RATE_LIMIT_WINDOW_MS); (drop entries older than 60s)
D. if (timestamps.length >= PICK_RATE_LIMIT_MAX) {
 - Respond with HTTP 429 and JSON:
   { "error": "RATE_LIMIT_EXCEEDED", "message": "Too many requests. Try again later." }
 - Frontend should show toast.error("Too many requests. Try again later.").
 - Do not proceed with further processing.
E. else {
 - timestamps.push(now);
 - pickRateLimitMap.set(telegram_id, timestamps);
 - Continue processing the request normally.
F. Notes:
 - This is in-memory only (per-process).
 - Use millisecond resolution for precision.
 - Place the rate-limit check before any DB FOR UPDATE locks to avoid holding locks while responding with 429.

6. Pick transaction
pick transaction happens in one Postgres Function.

Pseudocode (Postgres Function):

CREATE OR REPLACE FUNCTION pick_board(
    p_telegram_id BIGINT,
    p_target_board SMALLINT
) RETURNS JSON AS $$
DECLARE
    v_game_id           BIGINT;
    v_phase             TEXT;
    v_stake             NUMERIC(12,2);
    v_old_board         SMALLINT;
    v_prev_withdrawal   NUMERIC(12,2);
    v_prev_non          NUMERIC(12,2);
    v_target            RECORD;
    v_user              RECORD;
    v_total             NUMERIC(12,2);
    v_withdrawal_used   NUMERIC(12,2);
    v_non_withdrawal_used NUMERIC(12,2);
BEGIN
    -- 1. Get the current active game (latest game_id) efficiently
    SELECT game_id INTO v_game_id
    FROM games
    ORDER BY game_id DESC
    LIMIT 1;

    IF v_game_id IS NULL THEN
        RETURN json_build_object(
            'success', false,
            'error', 'NO_GAME',
            'message', 'No active game',
            'status_code', 500
        );
    END IF;

    -- 2. Lock the game row and check phase (also fetch stake)
    SELECT phase, stake_amount INTO v_phase, v_stake
    FROM games
    WHERE game_id = v_game_id
    FOR UPDATE;

    IF v_phase != 'picking' THEN
        RETURN json_build_object(
            'success', false,
            'error', 'PICKING_CLOSED',
            'message', 'Picking phase ended',
            'status_code', 409
        );
    END IF;

    -- 3. Silent abort for unregistered users (spec requirement)
    IF NOT EXISTS (SELECT 1 FROM users WHERE telegram_id = p_telegram_id) THEN
        RETURN json_build_object(
            'success', false,
            'error', 'USER_NOT_FOUND',
            'silent', true,
            'status_code', 204
        );
    END IF;

    -- 4. Find user's existing pick in this game (if any)
    SELECT board_id INTO v_old_board
    FROM player_picks
    WHERE game_id = v_game_id AND telegram_id = p_telegram_id
    FOR UPDATE;

    -- 5. Lock both boards (old and target) in ascending order (deadlock-proof)
    PERFORM board_id
    FROM player_picks
    WHERE board_id = p_target_board
       OR (v_old_board IS NOT NULL AND board_id = v_old_board)
    ORDER BY board_id
    FOR UPDATE;

    -- 6. Fetch the target board (now locked)
    SELECT * INTO v_target
    FROM player_picks
    WHERE board_id = p_target_board;

    -- 7. Ensure the target board exists
    IF v_target IS NULL THEN
        RETURN json_build_object(
            'success', false,
            'error', 'INVALID_BOARD',
            'message', 'Board number does not exist',
            'status_code', 400
        );
    END IF;

    -- 8. Check if board belongs to current game (if already assigned to someone)
    IF v_target.game_id IS NOT NULL AND v_target.game_id != v_game_id THEN
        RETURN json_build_object(
            'success', false,
            'error', 'BOARD_NOT_AVAILABLE',
            'message', 'This board is not available for the current game',
            'status_code', 409
        );
    END IF;

    -- 9. If target is taken by someone else in the current game → BOARD_TAKEN
    IF v_target.telegram_id IS NOT NULL
       AND v_target.game_id = v_game_id
       AND v_target.telegram_id != p_telegram_id THEN
        RETURN json_build_object(
            'success', false,
            'error', 'BOARD_TAKEN',
            'message', 'Board is selected by others',
            'status_code', 409
        );
    END IF;

    -- 10. Lock the user's wallet
    SELECT withdrawal_wallet, non_withdrawal_wallet INTO v_user
    FROM users
    WHERE telegram_id = p_telegram_id
    FOR UPDATE;

    -- =========================================================================
    -- CASE A: Unpick (clicked own slot)
    -- =========================================================================
    IF v_target.telegram_id = p_telegram_id AND v_target.game_id = v_game_id THEN
        UPDATE users
        SET withdrawal_wallet    = withdrawal_wallet    + v_target.withdrawal_used,
            non_withdrawal_wallet = non_withdrawal_wallet + v_target.non_withdrawal_used
        WHERE telegram_id = p_telegram_id;

        UPDATE player_picks
        SET telegram_id = NULL,
            withdrawal_used = 0,
            non_withdrawal_used = 0,
            picked_at = NULL
        WHERE board_id = p_target_board;

        RETURN json_build_object(
            'success', true,
            'action', 'unpick',
            'refunded', v_target.withdrawal_used + v_target.non_withdrawal_used
        );
    END IF;

    -- =========================================================================
    -- CASE B: First‑time pick (no previous pick)
    -- =========================================================================
    IF v_old_board IS NULL THEN
        v_total := v_user.withdrawal_wallet + v_user.non_withdrawal_wallet;
        IF v_total < v_stake THEN
            RETURN json_build_object(
                'success', false,
                'error', 'INSUFFICIENT_FUNDS',
                'message', 'Insufficient balance to pick',
                'status_code', 402
            );
        END IF;

        -- Priority: use non_withdrawal_wallet first
        v_non_withdrawal_used := LEAST(v_user.non_withdrawal_wallet, v_stake);
        v_withdrawal_used     := v_stake - v_non_withdrawal_used;

        UPDATE users
        SET withdrawal_wallet    = withdrawal_wallet    - v_withdrawal_used,
            non_withdrawal_wallet = non_withdrawal_wallet - v_non_withdrawal_used
        WHERE telegram_id = p_telegram_id;

        UPDATE player_picks
        SET telegram_id         = p_telegram_id,
            game_id             = v_game_id,
            withdrawal_used     = v_withdrawal_used,
            non_withdrawal_used = v_non_withdrawal_used,
            picked_at           = NOW()
        WHERE board_id = p_target_board;

        RETURN json_build_object(
            'success', true,
            'action', 'pick',
            'charged', json_build_object(
                'withdrawal_used', v_withdrawal_used,
                'non_withdrawal_used', v_non_withdrawal_used
            )
        );
    END IF;

    -- =========================================================================
    -- CASE C: Move‑pick (user already has a pick)
    -- =========================================================================
    SELECT withdrawal_used, non_withdrawal_used
    INTO v_prev_withdrawal, v_prev_non
    FROM player_picks
    WHERE board_id = v_old_board;

    -- Clear the old board
    UPDATE player_picks
    SET telegram_id = NULL,
        withdrawal_used = 0,
        non_withdrawal_used = 0,
        picked_at = NULL
    WHERE board_id = v_old_board;

    -- Assign the new board with the same used amounts
    UPDATE player_picks
    SET game_id             = v_game_id,
        telegram_id         = p_telegram_id,
        withdrawal_used     = v_prev_withdrawal,
        non_withdrawal_used = v_prev_non,
        picked_at           = NOW()
    WHERE board_id = p_target_board;

    RETURN json_build_object(
        'success', true,
        'action', 'move',
        'from', v_old_board,
        'to', p_target_board
    );
END;

Notes:
 - The server must verify the Telegram initData signature and extract the telegram_id. Do not trust telegram_id coming from the client body.
After commit, Supabase Realtime will broadcast UPDATE for the changed slot(s) — clients receive and update UI.

7. Picking lifecycle & transition to started (server timer)
 - On New game creation backend sets a timmer using games.picking_ends_at.
   - when the settimeout timer fires run:

const rows = await db.select({
  result: sql`transition_picking()`.as('result')
});
const result = rows[0]?.result;

CREATE OR REPLACE FUNCTION transition_picking()
RETURNS JSONB
LANGUAGE plpgsql
VOLATILE
AS $$
DECLARE
    v_game             games%ROWTYPE;
    v_config           game_config%ROWTYPE;
    v_player_count     INT;
    v_shuffled_nums    JSONB;
    v_prize_amount     NUMERIC(12,2);
    v_house_profit     NUMERIC(12,2);
    v_new_picking_ends TIMESTAMPTZ;
BEGIN
    -- 1. Lock the current (latest) game row
    SELECT * INTO STRICT v_game
    FROM games
    ORDER BY game_id DESC
    LIMIT 1
    FOR UPDATE;

    -- 2. Verify the game is in 'picking' phase
    IF v_game.phase != 'picking' THEN
        RAISE EXCEPTION 'Game is not in picking phase (current phase: %)', v_game.phase
            USING HINT = 'transition_picking() should only be called during picking phase.';
    END IF;

    -- 3. Lock all picked boards for this game (prevent concurrent picks)
    --    Order by board_id to avoid deadlocks with pick_board()
    PERFORM 1
    FROM player_picks
    WHERE game_id = v_game.game_id
      AND telegram_id IS NOT NULL
    ORDER BY board_id
    FOR UPDATE;

    -- 4. Count players who have picked a board
    SELECT COUNT(*)
    INTO v_player_count
    FROM player_picks
    WHERE game_id = v_game.game_id
      AND telegram_id IS NOT NULL;

    -- 5. Fetch the single row from game_config
    SELECT * INTO STRICT v_config
    FROM game_config
    WHERE id = 1
    FOR UPDATE;  -- lock to prevent concurrent changes

    -- 6. Decide whether to extend or start
    IF v_player_count < v_config.minimum_player THEN
        -- Extend picking phase
        v_new_picking_ends := NOW() + (v_config.picking_countdown_end_time * INTERVAL '1 second');

        UPDATE games
        SET picking_ends_at = v_new_picking_ends
        WHERE game_id = v_game.game_id;

        RETURN jsonb_build_object(
            'success', true,
            'action', 'extended',
            'player_count', v_player_count,
            'minimum_player', v_config.minimum_player,
            'new_picking_ends_at', v_new_picking_ends
        );
    ELSE
        -- Enough players → start the game
        -- Generate shuffled numbers 1..75 (random order)
        SELECT jsonb_agg(n ORDER BY random())
        INTO v_shuffled_nums
        FROM generate_series(1, 75) n;

        -- Calculate prize and house profit
        v_prize_amount := ROUND(
            (v_player_count * v_game.stake_amount * v_config.prize_percent) / 100.0,
            2
        );
        v_house_profit := ROUND(
            (v_player_count * v_game.stake_amount) - v_prize_amount,
            2
        );

        -- Update the game row to 'started'
        UPDATE games
        SET phase            = 'started',
            shuffled_nums    = v_shuffled_nums,
            prize_amount     = v_prize_amount,
            active_players   = v_player_count,
            house_profit     = v_house_profit,
            started_at       = NOW()
        WHERE game_id = v_game.game_id;

        RETURN jsonb_build_object(
            'success', true,
            'action', 'started',
            'game_id', v_game.game_id,
            'player_count', v_player_count,
            'prize_amount', v_prize_amount,
            'house_profit', v_house_profit,
            'shuffled_nums', v_shuffled_nums
        );
    END IF;
END;
$$;

//if the action is 'extended' set a using games.picking_ends_at for extending the picking phase. this must show a toast on the frontend: toast.error("Players must at least {games.minimum_player} for the game to start!")
//if the action is 'started' continue the started phase action.

8. Supabase Realtime & client UX notes
 - Clients subscribe to games and player_picks. RLS ensures visibility is restricted to active game.
 - On new games INSERT: clients detect new picking phase and reload wallet once.
 - If the new game has zero player_picks rows with that game_id yet, clients see empty grid (all gray) until players pick; that is expected.
 - When backend updates individual player_picks rows to game_id = new_game_id and telegram_id, Supabase Realtime emits UPDATE events and clients update tiles accordingly.
 - Keep client UI minimal: show spinner while waiting for server + realtime. Finalize color on realtime confirmation.
 - Footer preview is instantaneous because the client bundles all 500 bingo cards locally; when a pick becomes confirmed, the client uses its bundled BINGO_CARDS[board_id] to render the 5×5 preview with zero latency.

9. Error codes & toast mapping (frontend)
Code HTTP Toast text
BOARD_TAKEN 409 "Board is selected by others."
INSUFFICIENT_FUNDS 402 "Insufficient balance to pick."
PICKING_CLOSED 409 "Picking phase ended."
SERVER_ERROR 500 "Server error — try again."
 - Silent-abort case: when the server returns 204 No Content because the extracted telegram_id does not exist, the client must not display an error toast. (This is the defined silent-abort behavior.)
 - On 409 (BOARD_TAKEN or PICKING_CLOSED): refetch relevant slot(s / game state) to resync.
