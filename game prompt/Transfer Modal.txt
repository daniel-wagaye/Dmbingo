Transfer Modal 
UI (Frontend)
- Modal title: Transfer
- Wallet grid (read-only):
  - Withdrawable: x — from users.withdrawal_wallet (Postgres)
  - Non-Withdrawable: y — from users.non_withdrawal_wallet (Postgres)
- Fields:
  1. Wallet source (select):
    - Withdrawable → users.withdrawal_wallet
    - Non-Withdrawable → users.non_withdrawal_wallet
  2. Amount — number input only (prevents leading zeros on the client)
    - type="number"; min=10; max=1000; step=1
    - Frontend attribute: maxLength=4 (UX guard; note number inputs don’t natively enforce maxLength across all browsers, so also strip leading zeros and validate value on the client)
    - Client behavior: On every input/change the field should normalize value to remove any leading zeros (e.g., 0010 → 10) before submission.
   3. Recipient phone number (text input) — Ethiopian local format (10 digits)
    - Frontend attribute: maxLength=10
- Primary button: Send Transfer
  - disabled + loading indicator while request is in progress

Client-side validation
Run these checks before calling the API. On any failure, stop and show the exact toast:
  1. If amount < 10 →
     - toast.error("Transfer amount must be greater than or equal to 10")
  2. If amount > 1000 →
     - toast.error("Transfer amount must be less than or equal to 1000")
  3. If amount contains decimals →
     - toast.error("Only whole number please")
  4. If selected wallet balance < amount + estimated commission →
     - toast.error("Insufficient Balance")
  5. If recipient phone is not exactly 10 digits or does not start with 09 or 07 →
     - toast.error("The user number is not correct")
  6. Input-length enforcement (frontend UX):
     - Amount field shows maxLength=4 and normalizes input to remove leading zeros on change.
     - Phone field uses maxLength=10.
- Frontend checks are UX-only. Backend is authoritative and re-validates everything (including stripping leading zeros before length checks).

API Contract
- Endpoint: POST /api/transfers/send
- Request body:
{
  "telegram_id": 123456789,
  "from_wallet": "withdrawal",
  "amount": 250,
  "recipient_phone": "0912345678"
}

A) Rate limiting (per-user, in-memory sliding window)
- Use a module-scoped Map<telegram_id (number), number[]> to track request timestamps (in milliseconds or seconds — recommend milliseconds for precision).
- On each request (before any other processing):
  1. Get timestamps = rateLimitMap.get(telegram_id) || []
  2. Remove timestamps older than 60 seconds:
     - const now = Date.now();
     - timestamps = timestamps.filter(ts => now - ts < 60_000);
  3. If timestamps.length >= 5:
     - Return HTTP 429 with body { error: "RATE_LIMIT_EXCEEDED", message: "Too many transfers. Try again later." }
     - Frontend shows: toast.error("Too many transfers. Try again later.")
  4. Else:
     - Add current timestamp: timestamps.push(now)
     - rateLimitMap.set(telegram_id, timestamps)
     - Continue processing

B) Input sanitization, commission rules & recipient normalization
   (Must run before normalization, any DB lookup, or authoritative validation)
1. Sanitize inputs (always first)
  - Remove leading/trailing whitespace and delete all internal whitespace from both fields so they become pure digit strings.
  - After sanitization:
    - recipient_phone is digits-only
    - amount is a digit string
2. Strip leading zeros from amount before length checks (NEW)
  - Important change: before any backend length-based enforcement, remove all leading 0 characters from the sanitized amount string.
    - Example: "0009" → "9", "00100" → "100".
    - If the resulting string is empty (meaning the original was all zeros), treat it as "0" for numeric validation.
  - Then proceed to the length check described next.
3. Enforce input length limits on backend (authoritative enforcement)
  - After sanitization and after removing leading zeros:
    - If recipient_phone length ≠ 10 → return 400 → toast.error("The user number is not correct")
    - If the amount string (post-leading-zero-stripping) length > 4 → return 400 → toast.error("Transfer amount must be less than or equal to 1000")
      - Rationale: protects against excessively long inputs even if a client ignores frontend maxLength.
  - Note: length check is applied to the digit-count after removing leading zeros.
4. Parse and validate numeric amount
  - Parse the post-leading-zero amount string into an integer. If it is not a valid integer → return 400 → toast.error("Only whole number please").
  - Enforce numeric bounds: 10 <= amount <= 1000:
    - If amount < 10 → toast.error("Transfer amount must be greater than or equal to 10")
    - If amount > 1000 → toast.error("Transfer amount must be less than or equal to 1000")

5. Commission calculation (authoritative)
  - Commission = 2% of amount.
  - Round commission half-up to two decimals (so 0.995 → 1.00).
  - total = amount + commission.
  - Store amounts/commission as NUMERIC(12,2) in DB.
  - Frontend displays transfer fee Y exactly as returned by backend.
6. Balance sufficiency check
  - Compare selected wallet balance with total.
  - If insufficient → toast.error("Insufficient Balance")
7. Recipient phone normalization & lookup
  - Normalize sanitized phone (which already has no spaces):
    - Remove leading 0
    - Prefix +251
    - Example: 0912345678 → +251912345678
  - Lookup users by phone_number (DB stores normalized +251... format).
  - If user not found → toast.error("User doesn’t exist")
8. Execution order rule
  - Sanitization and leading-zero stripping must happen before:
    - any DB lookup,
    - authoritative length enforcement,
    - or balance checks,
  - to avoid false failures from formatting.

C) Atomic transfer (PostgreSQL transaction)
1. Begin transaction
2. Lock both sender and receiver rows in deadlock-safe order:
   SELECT * FROM users
   WHERE telegram_id IN ($sender_id, $recipient_id)
   ORDER BY telegram_id
   FOR UPDATE;
3. Recompute commission and total (authoritative):
   - commission = round half-up (amount * 0.02) to 2 decimal places
   - total = amount + commission
4. Re-check sender's selected wallet balance >= total
   - If insufficient → ROLLBACK transaction and return toast.error("Insufficient Balance")
5. Deduct total (amount + commission) from sender's selected wallet
6. Credit amount (excluding commission) to recipient's same wallet type
7. Insert into transfer_history:
   INSERT INTO transfer_history (
     sender_id,
     receiver_id,
     wallet,          -- 'withdrawal' or 'non_withdrawal' (exact value from from_wallet)
     amount,          -- transferred amount only
     commission,      -- calculated 2% fee
     created_at
   ) VALUES (
     $sender_id,
     $recipient_id,
     $from_wallet,
     $amount,
     $commission,
     NOW()
   );
8. COMMIT transaction

E) Post-commit actions
1. Fetch recipient’s fresh balances from DB
2. For sender name name use sender users.first_name 
   Send bot message to recipient:
     "You have received X from {sender_name} to your {wallet_type} wallet. Your total wallet is: Z."

F) Success response to sender
- Backend returns success payload
- Frontend shows:
  - toast.success("You have successfully transferred X to {phone}. Transfer fee: Y")
