Withdraw Modal
UI (Frontend)
- Modal title: Withdraw
- Balance display (read-only): Balance: x — from PostgreSQL users.withdrawal_wallet.
- Fields:
  1. Amount (number input) — minimum 100.
  2. Account holder full name (text).
  3. Bank (select): CBE | BOA | Telebirr | CBEbirr.
  4. Account number (text).
- Primary button: Request Withdrawal
  - Disable + spinner while submitting.
  - All feedback via toast.

Client-side validation
1. Amount: number and >= 100. Else → Toast.error("Withdraw amount must be greater than or equal to 100").
2. Quick balance check: if users.withdrawal_wallet < amount → Toast.error("Insufficient balance. Withdrawable Wallet: X").
3. Account holder name: max 20 chars, letters + spaces only. Else → toast.error("Please enter a valid account holder name").
4. Bank-specific account number:
  - CBE → 6 to 15 digits.
  - BOA → 6 to 15 digits.
  - Telebirr → 10 digits, must start with 09.
  - CBEbirr → 10 digits, must start with 09 or 07.
  - Else → toast.error("The account number is not correct").

Client → Backend API
POST /api/withdrawals/request — 
- Headers (required):
   Content-Type: application/json
   X-Telegram-Init-Data: <raw Telegram WebApp initData string>
- Body (JSON):
{
  "amount": 250,
  "bank": "CBE",
  "account_holder_name": "John Doe",
  "account_num": "1234567890123"
}

Backend authoritative flow

1. First step (mandatory): Verify the initData HMAC signature using the bot token (as described in the Telegram WebApp docs and your existing verifyInitData middleware).
   - If verification fails → return 401 { "error": "AUTH_FAILED", "message": "Invalid authentication data" }
   - If successful → extract telegram_id from the verified initData.
2. Use this extracted telegram_id for all further operations (rate limiting, user lookup, etc.).

3. Rate limiting (in-memory, per-user):
  - Maintain an in-memory Map<telegram_id, number[]> where each entry is an array of epoch-second (or ms) timestamps of recent attempts.
  - On each request:
    1. timestamps = map.get(telegram_id) || [].
    2. Remove any timestamps older than 60 seconds from timestamps.
    3. If timestamps.length >= 3 → return 429 { error: 'RATE_LIMIT_EXCEEDED', message: 'Too many requests. Try again later.' }.
    4. Else push now to timestamps, map.set(telegram_id, timestamps) and continue processing.
  - This keeps the backend safe from spam and uses almost zero memory even with hundreds of concurrent players.
  - (Note: this is an in-memory per-instance approach — suitable for single-instance or non-strict distributed setups.)

Per-user pending withdrawals check (immediately after the in-memory rate limiter)
- Query:
SELECT COUNT(*) as pending_count
FROM withdrawals_request
WHERE telegram_id = $1
  AND status = 'pending';
- Behavior:
  - If pending_count >= 5 → return 429 with body:
{ "error": "You already have 5 pending withdrawals. Please wait for processing." }
    Do not proceed further.
  - Else continue to the remaining checks and transaction.

(Step 1) Server-side input validations (MANDATORY — run before any DB mutation)
- Account holder full name
  - Max 20 chars; letters + spaces only.
  - Server regex example: ^[A-Za-z\s]{1,20}$.
  - If invalid → 400 → client: toast.error("Please enter a valid account holder name").
- Bank-specific account number
  - CBE → /^\d{6,15}$/
  - BOA → /^\d{6,15$/
  - Telebirr → /^09\d{8}$/
  - CBEbirr → /^(09|07)\d{8}$/
  - If invalid → 400 → client: toast.error("The account number is not correct").

(Step 4) Wallet verification (authoritative)
- Ensure users.withdrawal_wallet >= requested amount.
- If not → 400 → client shows toast.error("Insufficient Withdrawal Wallet").

(Step 4) Atomic DB transaction (insert request + debit wallet)
- Begin transaction.
- Insert new withdrawals_request with status='pending' and text_status='pending'.
- Decrement users.withdrawal_wallet atomically:

BEGIN;
INSERT INTO withdrawals_request
(telegram_id, bank, account_holder_name, account_num, amount, status, text_status, created_at)
VALUES ($1, $2, $3, $4, $5, 'pending', 'pending', now())
RETURNING withdrawal_id;

UPDATE users
SET withdrawal_wallet = withdrawal_wallet - $5
WHERE telegram_id = $1 AND withdrawal_wallet >= $5;

-- if update affected 0 rows => rollback => insufficient wallet

COMMIT;
  
 - If any step fails → rollback; return the appropriate 4xx/5xx error.

(Step 5) Trigger dmbingo-support-bot webhook (wake signal)
- Immediately after successful commit:

POST https://dmbingo-support-bot/webhook/withdraw-created
Header:
 Content-Type: application/json
 pass-key: 12345678 (.env key)
Body: { "event": "new" }
  - This is a wake-only webhook (no withdrawal_id).
  - If webhook fails: do not rollback the DB transaction or anything.

(Step 6) Respond to client
  - Success → 200 { success: true }. Client:
  - Close modal.
  - Refresh balances.
  - toast.promise("Your withdrawal is under progress. This may take a few minutes!").
  - send telegram message to the user: "Your withdrawal is under progress. This may take a few minutes!"

- Per-user pending limit exceeded → 429 { error: "You already have 5 pending withdrawals. Please wait for processing." } → client should show toast.error(...).
- Site-wide rate-limited → 429 { error: "Too many withdrawal requests. Try again in a minute." } → client shows toast.error(...).
- Other validation/lock errors → appropriate 4xx mapped to exact toast messages.
- Server error → 5xx → toast.error("Something went wrong. Please try again.").
