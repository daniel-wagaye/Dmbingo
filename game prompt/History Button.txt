History Button:
This Prompt describes the complete History Modal: POST /api/history, per-request Telegram initData header auth (no sessions), in-memory sliding-window rate limiter, Supabase cursor pagination (limit=100), frontend masking/reveal, Amharic+English status mapping, and full row requirements. Frontend must never show DB ids.

UX summary
 - Opens only when user taps History / ታሪክ.
 - Top selector: ALL | WIN | WITHDRAW | TRANSFER | COUPON (default ALL). No search/date/export.
 - Initial fetch: 100 rows. “Load More” loads next 100; if returned rows <100 or next_cursor==null → disable Load More.
 - Show centered spinner while fetching initial page; small spinner in Load More while fetching more. Disable selector & Load More while fetching.
 - Rows ordered created_at DESC, id DESC. Backend may include internal ids for cursor only; frontend must not display ids.

API — contract (exact)
POST /api/history

Headers (MANDATORY):
Content-Type: application/json
X-Telegram-Init-Data: <raw Telegram WebApp initData string>

Body:
{ "filter":"all", "limit":100, "cursor": null }

 - filter ∈ {all, win, withdraw, transfer, coupon}
 - limit client sends 100; server enforces <=100.
 - cursor opaque (base64 JSON: {"created_at":"...", "id":"..."}) or null.

Response:
{ "success": true, "rows":[...], "next_cursor":"<opaque|null>" }
Each row must include a title and fields below. No UI-visible id.

Row shapes (server → frontend)

Withdraw
 - type:"withdraw", title:"Withdrawal", amount, currency:"ETB", bank, account_num (FULL), account_holder_name, status (pending|approved|declined), created_at

Transfer
 - type:"transfer", title:"Transfer Sent"|"Transfer Received", amount (negative if sent), wallet, direction (sent|received), commission, account_num (if stored), created_at

Coupon
 - type:"coupon", title:"Coupon", amount (credited_amount), credit_wallet (withdrawal|non_withdrawal), created_at

Win
 - type:"win", title:"Win", amount, created_at

Frontend rules (explicit)
 - Masking: show masked account_num by default (e.g., ******1234). Show toggles reveal locally.
 - Status badge (withdraw only): map raw status to text/color using users.language:
 - English: pending→Pending, approved→Approved, declined→Rejected
 - Amharic: pending→በመጠባበቅ ላይ, approved→ተፈቅዷል, declined→ተቀባይነት አልተሰጠውም
 - Colors: Yellow #F5C94A, Green #34D399, Red #F87171. Badge top-right of withdrawal card.
- Transfer rows: show direction and counterparty (masked phone or username) if desired.
- Coupon rows: show credit_wallet as human label (Withdrawal Wallet / Playing Wallet; localize).

Backend processing (per-request)
1. Read X-Telegram-Init-Data; if missing → 401.
2. Verify initData HMAC per Telegram docs: build data_check_string from sorted params, secret=sha256(botToken), compute HMAC-SHA256, compare with hash using timing-safe compare. If invalid → 401. Extract telegram_id.
3. Rate-limit via in-memory sliding-window keyed by telegram_id. If exceeded → 429.
4. Validate filter, limit<=100, parse cursor.
5. Query Supabase/Postgres user_history view (union of your tables) using cursor-based SQL (created_at, id) < (cursor.created_at, cursor.id) and ORDER BY created_at DESC, id DESC LIMIT limit.
6. Return rows (no visible ids) and next_cursor (null if none). Server may include internal id only for cursor encoding.

In-memory sliding-window limiter (single-instance)
Defaults: LIMIT=10, WINDOW_MS=60000. Pseudocode:

const windows = new Map(); // Map<telegram_id, timestamps[]>
function isAllowed(id){
  const now=Date.now(), arr=windows.get(id)||[];
  while(arr.length && now-arr[0]>WINDOW_MS) arr.shift();
  if(arr.length>=LIMIT) return false;
  arr.push(now); windows.set(id,arr); return true;
}
Call after initData verification.

Supabase view guidance (example)
Create user_history as UNION ALL of:
 - withdrawals_request → include account_num, status, created_at
 - winners_history → credited_amount AS amount, won_at AS created_at
 - coupon_history → credited_amount, credit_wallet, claimed_at
 - transfer_history → compute direction & signed amount, created_at
Ensure indexes on (telegram_id, created_at DESC, id) for each table.

Cursor encoding
 - Encode last returned row {created_at,id} as base64 JSON. Server decodes to resume with (created_at, id) comparator to avoid duplicates.

Error mapping (client)
401 → toast.error("Authentication failed. Please re-open the app.")
429 → toast.error("Too many requests. Please slow down.")
500 → toast.error("Something went wrong. Please try again.")
