Backend — API contract (authoritative)

Endpoint: PATCH /api/user/language
Headers: Content-Type: application/json, X-Telegram-Init-Data required and verified.
Body: { "language": "en" } or { "language": "am" }

Responses
200 { "success": true, "language": "am" }
400 { "error": "INVALID_LANGUAGE" } or { "error": "USER_NOT_FOUND" }
401 { "error": "AUTH_FAILED" }
429 { "error": "RATE_LIMIT_EXCEEDED" }
500 { "error": "INTERNAL" }

In-Memory Sliding Window Rate Limiter (single instance)
 - Window: 60,000 ms
 - Limit: 5 changes per window per telegram_id
 - Note: resets on server restart (acceptable for single instance).

Module scope implementation:
const WINDOW_MS = 60_000;
const LIMIT = 5;
const languageRateMap = new Map(); // Map<telegram_id, number[] timestamps>

function isLanguageChangeAllowed(telegram_id) {
  const now = Date.now();
  let arr = languageRateMap.get(telegram_id) || [];
  arr = arr.filter(ts => now - ts < WINDOW_MS); // keep only recent
  if (arr.length >= LIMIT) {
    languageRateMap.set(telegram_id, arr);
    return false;
  }
  arr.push(now);
  languageRateMap.set(telegram_id, arr);
  return true;
}
 - Call this before starting DB transaction. If false → return 429.

Atomic DB update — server logic (transactional)
 - Goal: ensure users.language update is atomic and consistent; no audit table; rate limit enforced in memory before transaction.

Pseudocode (Node/Express + pg):
async function handlePatchLang(req, res){
  const init = req.header('X-Telegram-Init-Data');
  const telegram_id = verifyInitAndGetTelegramId(init);
  if(!telegram_id) return res.status(401).json({error:'AUTH_FAILED'});

  const newLang = req.body?.language;
  if(!['en','am'].includes(newLang)) return res.status(400).json({error:'INVALID_LANGUAGE'});

  // in-memory rate limit (single-instance)
  if(!isLanguageChangeAllowed(telegram_id)){
    return res.status(429).json({error:'RATE_LIMIT_EXCEEDED'});
  }

  const client = await pool.connect();
  try {
    await client.query('BEGIN');

    // atomic update
    const result = await client.query(
      'UPDATE users SET language=$1 WHERE telegram_id=$2 RETURNING language',
      [newLang, telegram_id]
    );

    if(result.rowCount === 0){
      await client.query('ROLLBACK');
      return res.status(400).json({error:'USER_NOT_FOUND'});
    }

    await client.query('COMMIT');
    return res.status(200).json({success:true, language: result.rows[0].language});

  } catch(err){
    await client.query('ROLLBACK').catch(()=>{});
    console.error(err);
    return res.status(500).json({error:'INTERNAL'});
  } finally {
    client.release();
  }
}
 - BEGIN → UPDATE → COMMIT ensures atomic write and no partial state.

Backend contract & behavior

Endpoint: PATCH /api/user/name
Headers required: X-Telegram-Init-Data: <raw Telegram WebApp initData string>
Body: { "first_name": "string" }

High-level flow (must run in this order):
1. Verify initData HMAC (Telegram docs). If invalid/missing → 401.
2. Extract telegram_id from verified initData.
3. Server-side validation
  - name = trim(body.first_name).slice(0,12) (enforce max 12).
  - If name.length === 0 → set name = 'Player'.
  - If not match /^[\p{L}\s'-]{1,12}$/u → 400 { error: "INVALID_NAME" }.
4. In-memory sliding-window rate limiter (run after auth, before DB work):
  - Module-scope Map: Map<telegram_id, number[]> timestamps (ms).
  - WINDOW_MS = 600_000 (10 minutes), LIMIT = 5.
  - Filter timestamps to recent window; if arr.length >= LIMIT → return 429.
  - Else push now and continue.

5. Atomic DB transaction:
BEGIN;
UPDATE users
  SET first_name = $1, updated_at = now()
  WHERE telegram_id = $2
  RETURNING first_name;
-- if 0 rows returned -> ROLLBACK -> 400 { error: "USER_NOT_FOUND" }
COMMIT;

6. Return 200 { success: true, first_name: "<saved_name>" }.

Notes
 - Enforce trimming & maxlength on both client & server: server is authoritative.
 - Use UPDATE ... RETURNING inside a transaction to guarantee atomic write.
 - Rate limiter is in-memory and resets on process restart (acceptable single-instance).
 - Always verify initData before any rate-limit or DB checks.
